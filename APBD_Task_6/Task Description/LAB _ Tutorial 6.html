Clinic Appointments REST API with ADO.NET

In this exercise you will build an ASP.NET Core Web API based on controllers. The goal is to practice SQL Server communication without Entity Framework: SqlConnection, SqlCommand, SqlDataReader, SQL parameters, DTOs, and basic CRUD operations.

Business Context

A medical clinic needs a small backend for managing patient appointments. The system stores patients, doctors, doctor specializations, and appointments. A receptionist should be able to list appointments, inspect one appointment, create a new appointment, update appointment data, and delete an appointment that should no longer remain as an active booking.

Important. Do not use Entity Framework in this exercise. All database communication must be implemented manually with ADO.NET.

What You Need to Build

Create an ASP.NET Core Web API in C# with a controller for the Appointment resource. Data must be stored in SQL Server. Use Microsoft.Data.SqlClient to execute database commands.

Endpoint Scope

Method Endpoint Description GET /api/appointments Returns appointments with basic patient data. GET /api/appointments/{idAppointment} Returns details of one appointment. POST /api/appointments Creates a new appointment. PUT /api/appointments/{idAppointment} Updates an existing appointment. DELETE /api/appointments/{idAppointment} Deletes an appointment.

Most important. Endpoints must return DTOs, and all values coming from route, query string, or request body must be passed to SQL through parameters.

Technical Requirements

1. Project and dependencies

  • Create an ASP.NET Core Web API project based on controllers.
  • Add the Microsoft.Data.SqlClient package.
  • Configure controllers in Program.cs with AddControllers() and app.MapControllers().
dotnet add package Microsoft.Data.SqlClient

2. Connection configuration

Place the connection string in appsettings.json.

{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost,1433;Database=ClinicAdoNet;User Id=sa;Password=YourStrong@Passw0rd;TrustServerCertificate=True"
  }
}

Read it through IConfiguration:

var connectionString = configuration.GetConnectionString("DefaultConnection");

3. DTOs and mapping

  • Do not return database table structures directly.
  • Map SqlDataReader results to DTOs.
  • The list DTO can be shorter than the details DTO.
public class AppointmentListDto
{
    public int IdAppointment { get; set; }
    public DateTime AppointmentDate { get; set; }
    public string Status { get; set; } = string.Empty;
    public string Reason { get; set; } = string.Empty;
    public string PatientFullName { get; set; } = string.Empty;
    public string PatientEmail { get; set; } = string.Empty;
}

4. SQL parameters

  • Do not build SQL queries with string interpolation.
  • Use a SQL parameter for every user input.
  • This applies to values from route, query string, and request body.
await using var command = new SqlCommand("""
    SELECT IdAppointment, AppointmentDate, Status, Reason
    FROM dbo.Appointments
    WHERE IdAppointment = @IdAppointment;
    """, connection);

command.Parameters.Add("@IdAppointment", SqlDbType.Int).Value = idAppointment;

Warning. Queries built with $"..." and user-provided values are vulnerable to SQL Injection. In this exercise, all queries must be parameterized.

5. HTTP statuses

  • 200 OK for successful reads and updates,
  • 201 Created after creating an appointment,
  • 204 No Content after deleting an appointment,
  • 400 Bad Request for invalid input,
  • 404 Not Found when a resource does not exist,
  • 409 Conflict when an operation violates a business rule.

Endpoint Logic

GET /api/appointments

This endpoint returns a list of appointments with basic patient data. It should support two optional query string parameters: status and patientLastName.

GET /api/appointments?status=Scheduled&patientLastName=Kowalska

For the first ADO.NET endpoint, a simple JOIN between two tables is enough: Appointments and Patients. Doctor and specialization data can be returned by the details endpoint.

SELECT
    a.IdAppointment,
    a.AppointmentDate,
    a.Status,
    a.Reason,
    p.FirstName + N' ' + p.LastName AS PatientFullName,
    p.Email AS PatientEmail
FROM dbo.Appointments a
JOIN dbo.Patients p ON p.IdPatient = a.IdPatient
WHERE (@Status IS NULL OR a.Status = @Status)
  AND (@PatientLastName IS NULL OR p.LastName = @PatientLastName)
ORDER BY a.AppointmentDate;

GET /api/appointments/{idAppointment}

This endpoint returns details of one appointment. Return 404 Not Found when it does not exist. The details DTO may include patient email, phone number, doctor license number, internal notes, and record creation date.

POST /api/appointments

This endpoint creates a new appointment with status Scheduled.

{
  "idPatient": 1,
  "idDoctor": 2,
  "appointmentDate": "2026-05-20T10:30:00",
  "reason": "Control visit"
}
  • The patient must exist and be active.
  • The doctor must exist and be active.
  • The appointment date cannot be in the past.
  • The reason cannot be empty and should have at most 250 characters.
  • The doctor cannot already have another scheduled appointment at exactly the same time.

Return 201 Created after successful creation. Return 409 Conflict when the appointment time conflicts with another appointment.

PUT /api/appointments/{idAppointment}

This endpoint updates an existing appointment.

{
  "idPatient": 1,
  "idDoctor": 1,
  "appointmentDate": "2026-05-22T12:00:00",
  "status": "Scheduled",
  "reason": "Rescheduled cardiology consultation",
  "internalNotes": "Patient asked for a later hour."
}
  • Return 404 Not Found if the appointment does not exist.
  • The patient and doctor must exist and be active.
  • Status must be one of: Scheduled, Completed, Cancelled.
  • If the appointment is already Completed, do not allow changing its date.
  • When changing the date, check conflicts with other appointments of the same doctor.

DELETE /api/appointments/{idAppointment}

This endpoint deletes an appointment. Return 404 Not Found if it does not exist. If the appointment has status Completed, do not delete it and return 409 Conflict. Return 204 No Content after successful deletion.

Suggested Project Organization

  • Controllers folder with AppointmentsController,
  • DTOs folder for request and response classes,
  • optional Services folder with AppointmentService,
  • connection string in appsettings.json.

You do not need a complex architecture. Keep the code simple and readable. If the controller becomes too long, extract logic into a service.

Suggested Work Order

  1. Create a Web API project and add Microsoft.Data.SqlClient.
  2. Run 01_create_and_seed_clinic.sql.
  3. Add the connection string in appsettings.json.
  4. Prepare DTOs.
  5. Implement GET /api/appointments and verify the first database read.
  6. Add GET /api/appointments/{idAppointment} and 404 handling.
  7. Add POST with validation and appointment time conflict handling.
  8. Add PUT with update logic and business rules.
  9. Add DELETE.
  10. Test everything in Swagger, Postman, or an .http file.

Testing Scope

After preparing the application, test not only valid cases but also invalid data and business conflicts.

  1. Get all appointments.
  2. Get appointments for one doctor through query string.
  3. Get one existing appointment.
  4. Check 404 Not Found for a non-existing appointment.
  5. Create a valid appointment.
  6. Try to create an appointment in the past and check 400 Bad Request.
  7. Try to create two appointments for the same doctor at the same time and check 409 Conflict.
  8. Update an appointment.
  9. Delete an appointment with status Scheduled.
  10. Try to delete an appointment with status Completed and check 409 Conflict.

Things to Watch Out For

  • Do not return table models directly as API responses.
  • Do not use string interpolation for SQL queries.
  • Make sure connections are disposed with await using.
  • Use async methods: OpenAsync, ExecuteReaderAsync, ExecuteScalarAsync, ExecuteNonQueryAsync.
  • Mapping from SqlDataReader to DTOs can be manual.
  • Business rules should return readable errors instead of raw SQL exceptions.

What This Exercise Practices

  • connecting ASP.NET Core to SQL Server with ADO.NET,
  • executing SELECT, INSERT, UPDATE, and DELETE,
  • mapping SqlDataReader results to DTOs,
  • designing REST endpoints with correct HTTP statuses,
  • validating simple business rules,
  • using SQL parameters to protect against SQL Injection.
